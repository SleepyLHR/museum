# 后端功能需求文档

> 项目：文物拼多多 · 博物馆拼图游戏
> 版本：v2.0（引入 Node.js 后端）
> 部署环境：Linux 云服务器 + Nginx + Node.js

---

## 1. 项目背景

当前为纯前端 H5 应用，所有数据存储在浏览器 localStorage 中，存在以下局限：

| 问题 | 影响 |
|------|------|
| localStorage 隔离 | 换设备/清缓存后数据全部丢失 |
| 证书编号基于时间戳 | `BM2025+7位数字`，无法实现递增编号 |
| 无服务端 | 无法做排行榜、用户统计 |
| 编号不可验证 | 无法判断证书真伪、无法防伪造 |

引入 Node.js 后端后，核心收益：
- **递增证书编号** 000001→999999，逢特殊数字自动识别
- **用户持久化** 换设备/清缓存后可恢复身份
- **排行榜** 日榜 + 总榜

## 2. 架构设计

```
┌──────────────────────────────────────────────────┐
│                    Nginx (:80)                    │
│                                                  │
│  /api/*  ──→ proxy_pass http://127.0.0.1:3001   │
│  /*      ──→ 静态文件 (HTML/CSS/JS/images)       │
└──────────────┬────────────────────┬──────────────┘
               │                    │
    ┌──────────▼──────────┐  ┌─────▼──────────────┐
    │  Node.js (:3001)    │  │  静态文件目录        │
    │  museum-server.js   │  │  index.html         │
    │  data.db (SQLite)   │  │  config.json        │
    │                     │  │  js/ css/ images/   │
    └─────────────────────┘  └────────────────────┘
```

**技术选型：**

| 组件 | 选择 | 理由 |
|------|------|------|
| 运行时 | Node.js 18+ | 与前端语言统一 |
| 框架 | 原生 `http` 模块 | 功能简单，无需 Express |
| 数据库 | SQLite (better-sqlite3) | 单文件零配置，适合中小规模 |
| 进程管理 | pm2 | 自动重启、日志管理 |
| 端口 | 3001（内网） | Nginx 反向代理到 80 |

**依赖包：** 仅 `better-sqlite3` 一个（同步 SQLite 驱动，性能好、API 简洁）

## 3. 数据库设计 (SQLite)

### 3.1 users — 用户表

```sql
CREATE TABLE users (
  id           TEXT PRIMARY KEY,     -- "U" + base36时间戳, 例: U1a2b3c4
  token        TEXT NOT NULL UNIQUE, -- 32位hex随机字符串, 用于API认证
  nickname     TEXT DEFAULT '神秘玩家',
  created_at   TEXT NOT NULL,       -- ISO 8601
  last_active_at TEXT NOT NULL
);
```

**设计要点：**
- `id` 与 `token` 分离：id 公开显示，token 私密认证
- 昵称可修改，与证书中锁定的昵称独立

### 3.2 certificates — 证书表

```sql
CREATE TABLE certificates (
  cert_number  TEXT PRIMARY KEY,    -- "000001" ~ "999999"
  user_id      TEXT NOT NULL,
  nickname     TEXT NOT NULL,       -- 锁定快照（通关时的昵称）
  total_time   INTEGER NOT NULL,    -- 总用时（秒），锁定快照
  is_special   INTEGER DEFAULT 0,   -- 0=普通 1=特殊号码
  prize        TEXT,                -- 奖品名称，普通为 NULL
  created_at   TEXT NOT NULL,       -- ISO 8601
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**设计要点：**
- `nickname` 和 `total_time` 是通关瞬间的快照，不随后续修改变化
- `is_special` 和 `prize` 由服务端在生成编号时自动判断

### 3.3 cert_counter — 编号计数器

```sql
CREATE TABLE cert_counter (
  id            INTEGER PRIMARY KEY DEFAULT 1,
  current_value INTEGER NOT NULL DEFAULT 0
);
-- 初始插入: INSERT INTO cert_counter (current_value) VALUES (0);
```

**递增逻辑（伪代码）：**
```
BEGIN TRANSACTION
  UPDATE cert_counter SET current_value = current_value + 1
  SELECT current_value FROM cert_counter
COMMIT
→ 格式化为 6 位: String(value).padStart(6, '0')
```

### 3.4 scores — 总榜成绩表

```sql
CREATE TABLE scores (
  user_id    TEXT PRIMARY KEY,
  nickname   TEXT NOT NULL,
  total_time INTEGER NOT NULL,     -- 当前最佳总用时（秒）
  updated_at TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**设计要点：**
- 每个用户只有一条记录（PRIMARY KEY = user_id）
- 每次通关后更新（仅当新成绩更优时）
- 排行榜查询：`ORDER BY total_time ASC`

### 3.5 daily_scores — 日榜成绩表

```sql
CREATE TABLE daily_scores (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    TEXT NOT NULL,
  nickname   TEXT NOT NULL,
  total_time INTEGER NOT NULL,
  score_date TEXT NOT NULL,        -- "2026-05-09"
  created_at TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX idx_daily_date_time ON daily_scores(score_date, total_time);
```

**设计要点：**
- 每天可能有多条记录（用户多次刷新成绩）
- 日榜取当天 `MIN(total_time) GROUP BY user_id`
- 每天 00:00 自动切换日期（查询时按 `score_date` 过滤）

## 4. API 设计

全部接口前缀：`/api`

### 4.1 用户类

#### POST /api/user/create

> 首次访问时调用，创建匿名用户

请求体：
```json
{}
```

响应：
```json
{
  "userId": "U1a2b3c4",
  "token": "a1b2c3d4e5f6...32位hex",
  "nickname": "神秘玩家",
  "isNew": true
}
```

错误处理：
- 服务端异常 → 返回 500，前端降级使用 localStorage 模式

#### GET /api/user/info

> 获取当前用户信息

请求头：
```
Authorization: Bearer <token>
```

响应：
```json
{
  "userId": "U1a2b3c4",
  "nickname": "神秘玩家",
  "createdAt": "2026-05-09T10:30:00.000Z"
}
```

认证失败 → 401

#### PUT /api/user/nickname

> 修改昵称

请求头：
```
Authorization: Bearer <token>
```
请求体：
```json
{ "nickname": "张三" }
```

响应：
```json
{ "success": true, "nickname": "张三" }
```

#### POST /api/user/recover

> localStorage 丢失后，凭证书编号找回身份

请求体：
```json
{
  "certNumber": "000123",
  "nickname": "张三"
}
```

响应：
```json
{
  "success": true,
  "userId": "U1a2b3c4",
  "token": "新的32位hex",
  "certNumber": "000123",
  "totalTime": 360
}
```

失败：
```json
{ "success": false, "message": "证书编号与昵称不匹配" }
```

**安全设计：**
- 校验 `certNumber` + `nickname` 双重匹配
- 恢复成功后生成新 token，旧 token 失效
- 同一证书只能被恢复有限次数（建议 3 次）

### 4.2 证书类

#### POST /api/cert/apply

> 首次通关时申请证书编号

请求头：
```
Authorization: Bearer <token>
```
请求体：
```json
{
  "totalTime": 360,
  "nickname": "张三"
}
```

响应：
```json
{
  "certNumber": "000888",
  "isSpecial": true,
  "prize": "三等奖 - 精美文创礼品",
  "totalCerts": 888
}
```

**服务端逻辑：**
1. 验证 token → 获取 userId
2. 检查该用户是否已领过证书 → 若已领，返回已有编号（幂等）
3. 原子递增计数器 → 生成 6 位编号
4. 检测特殊号码规则 → 匹配则标记
5. 写入 certificates 表
6. 返回结果

**特殊号码检测规则（配置文件 `special-rules.json`）：**

```json
{
  "specials": [
    { "rule": "endsWith", "value": "888", "prize": "三等奖 - 精美文创礼品" },
    { "rule": "endsWith", "value": "666", "prize": "三等奖 - 精美文创礼品" },
    { "rule": "endsWith", "value": "000", "prize": "参与奖 - 博物馆纪念贴纸" },
    { "rule": "exact",  "value": "000001", "prize": "特别奖 - 首位通关大礼包" },
    { "rule": "exact",  "value": "100000", "prize": "里程碑奖 - 十万通关纪念品" },
    { "rule": "exact",  "value": "500000", "prize": "里程碑奖 - 五十万通关纪念品" },
    { "rule": "exact",  "value": "999999", "prize": "终极奖 - 百万通关大礼包" },
    { "rule": "pattern","value": "^(\\d)\\1{5}$", "prize": "二等奖 - 限量文创套装" }
  ]
}
```

规则说明：
- `endsWith`: 编号以指定数字结尾
- `exact`: 完全匹配
- `pattern`: 正则匹配（例中匹配六位相同数字如 111111、222222...888888）
- 规则按数组顺序匹配，命中第一个即停止

## 6. 完整业务流程

### 6.1 新用户首次访问

```
用户打开页面
  │
  ▼
app.js init()
  │
  ├→ 检查 localStorage 是否有 userId/token
  │   ├→ 有 → 调用 GET /api/user/info 验证
  │   │        ├→ 成功 → 正常模式
  │   │        └→ 失败(401) → 重新注册
  │   └→ 无 → 调用 POST /api/user/create
  │            ├→ 成功 → 存储 userId+token 到 localStorage
  │            └→ 失败 → 降级为 localStorage 模式
  │
  ▼
正常使用（游戏、图库、设置...）
```

### 6.2 首次通关流程

```
完成第5关（最后一关）
  │
  ▼
onCompletion() → 首次通关检测
  │
  ▼
POST /api/cert/apply (token, totalTime, nickname)
  │
  ▼
服务端：
  1. 原子递增计数器 → 生成 6 位编号
  2. 检测特殊号码规则
  3. 写入 certificates 表
  4. 返回 { certNumber, isSpecial, prize }
  │
  ▼
POST /api/score/submit (token, totalTime, nickname)
  │
  ▼
前端展示首次通关弹窗
  ├→ 普通编号 → 标准弹窗
  └→ 特殊编号 → 带中奖提示的弹窗
  │
  ▼
setFirstCompletion() → localStorage 快照
```

### 6.3 localStorage 丢失后恢复

```
用户清缓存后重新打开页面
  │
  ▼
app.js init() → localStorage 无 userId/token
  │
  ▼
POST /api/user/create → 创建新用户（新 userId）
  │
  ▼
用户进入"找回证书"页面
  │
  ├→ 输入证书编号 + 昵称
  │
  ▼
POST /api/user/recover (certNumber, nickname)
  │
  ▼
服务端验证：
  ├→ certificates 表找到匹配 → 返回原 userId + 新 token
  │   └→ 前端更新 localStorage → 恢复身份
  └→ 不匹配 → 提示错误
```

## 7. 错误处理与降级

### 7.1 降级策略

| 场景 | 行为 |
|------|------|
| 服务端完全不可达 | `serverAvailable = false`，全部功能降级为 localStorage 模式 |
| 创建用户失败 | 使用本地生成的 `localUserId`，后续 API 调用跳过 |
| 证书申请失败 | 回退到原有时间戳编号 `BM2025+7位数字` |
| 排行榜加载失败 | 显示"排行榜暂不可用" |
| 成绩提交失败 | 静默失败，不影响游戏流程 |

### 7.2 状态检测

```javascript
// app.js
var serverAvailable = true;

function checkServer() {
  return fetch('/api/cert/stats')
    .then(function(r) { return r.ok; })
    .catch(function() {
      serverAvailable = false;
      return false;
    });
}
```

## 9. 部署配置

### 9.1 Nginx 配置

```nginx
# /etc/nginx/conf.d/museum.conf
server {
    listen 80;
    server_name _;

    root /opt/museum/h5;
    index index.html;

    # API 代理到 Node.js
    location /api/ {
        proxy_pass http://127.0.0.1:3001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 静态文件
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

## 10. 安全考虑

| 方面 | 措施 |
|------|------|
| 编号伪造 | 证书编号仅在服务端生成，客户端无法伪造 |
| 身份冒用 | token 为 32 位随机 hex，暴力破解不可行 |
| 恢复滥用 | 同一证书恢复次数限制（3次），防止恶意尝试 |
| SQL 注入 | 使用 `better-sqlite3` 参数化查询，天然防注入 |
| 并发编号 | SQLite 事务保证原子递增，不会重复 |
| 接口限流 | 可选：Nginx `limit_req` 模块限制 API 频率 |
